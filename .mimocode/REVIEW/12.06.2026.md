# Кодовый ревью: Анализ проекта Talker

## Обзор проекта

**Talker** — система мгновенных сообщений (аналог Telegram/WhatsApp) на Go, построенная как распределённая система микросервисов с gRPC. Проект находится на ранней стадии разработки.

**Структура:**
- `services/user/` — сервис аутентификации (наиболее成熟)
- `services/message/` — сервис сообщений (частично реализован)
- `services/chat/`, `services/poll/` — только proto-определения
- `server-gateway/` — каркас API-шлюза (пустой)
- `pkg/protos/` — общие protobuf-определения

## Критические ошибки (P0)

### 1. Data race на логере — каждое 요청 мутирует общее состояние
**Файлы:** `services/message/internal/service/message.go:33,49,77,95,115`, `services/user/internal/service/user.go:33,61,89,115`

```go
// НЕПРАВИЛЬНО: мутирует указатель на логер
s.log = s.log.With(zap.Any("request", req))

// ПРАВИЛЬНО: использовать локальную переменную
log := s.log.With(zap.Any("request", req))
```

**Последствие:** При конкурентных запросах данные одного запроса попадают в логи другого. Это data race, который приводит к некорректным логам и potential crashes.

### 2. Код не компилируется — message service
**Файлы:**
- `services/message/cmd/server/main.go:3-5` — пустой `main()`
- `services/message/internal/app/app.go:20` — переменная `app` не объявлена
- `services/message/internal/storage/postgres/feature.go:86-91` — незавершённый SQL-запрос

### 3. Неправильный импорт — message service импортирует user service
**Файл:** `services/message/internal/app/grpc/app.go:9`

```go
grpc2 "github.com/north-fy/talker/services/user/internal/grpc"
```

Сервис сообщений импортирует внутренний пакет сервиса пользователей. В микросервисной архитектуре сервисы не должны зависеть от внутренних пакетов друг друга.

### 4. Несоответствие параметров SQL-запроса
**Файл:** `services/message/internal/storage/postgres/message.go:34,51`

SQL имеет 5 плейсхолдеров (`$1-$5`), но передаётся 6 аргументов. Это вызовет ошибку runtime.

### 5. JWT-секрет может быть пустой строкой
**Файл:** `services/user/internal/config/const.go:13`

```go
var JwtSecret = os.Getenv("JWT_SECRET")
```

Если переменная окружения не задана, `JwtSecret` будет пустой строкой. Токены, подписанные пустым ключом, легко подделать.

## Серьёзные ошибки (P1)

### 6. Пароли логируются в открытом виде
**Файлы:** `services/user/internal/service/user.go:33,61`

```go
s.log = s.log.With(zap.Any("model.User", user)) // user содержит пароль
```

### 7. Одно соединение с БД вместо пула
**Файлы:** `services/message/internal/storage/postgres/postgres.go:14`, `services/user/internal/storage/postgres/storage.go:15`

Используется `pgx.Conn` (одно соединение) вместо `pgxpool.Pool` (пул соединений). При конкурентных запросах все операции сериализуются через одно соединение.

### 8. Все ошибки gRPC сворачиваются в одну
**Файлы:** `services/user/internal/grpc/server.go:41,57,70,87`, `services/message/internal/grpc/message.go:37,84`

Все ошибки возвращают `codes.Internal` с текстом `"invalid argument"`. Клиент не может отличить "не найдено" от "внутренняя ошибка".

### 9. Panic в конструкторах вместо возврата ошибок
**Файлы:** `services/message/internal/storage/postgres/postgres.go:21,27`, `services/user/internal/storage/postgres/storage.go:22,28`

```go
// НЕПРАВИЛЬНО: panic при ошибке подключения
panic(err)

// ПРАВИЛЬНО: возврат ошибки
return nil, fmt.Errorf("connect to postgres: %w", err)
```

### 10. Unsafe type assertion без проверки
**Файлы:** `services/message/internal/service/message.go:35`, `services/user/internal/service/user.go:33`

```go
// НЕПРАВИЛЬНО: паника при отсутствии ключа в контексте
id := ctx.Value(models.UserIDKey).(int64)

// ПРАВИЛЬНО: проверка с помощью двух значений
id, ok := ctx.Value(models.UserIDKey).(int64)
if !ok {
    return nil, status.Error(codes.Unauthenticated, "user ID not found in context")
}
```

## Средние ошибки (P2)

### 11. SQL LIKE injection в поиске
**Файл:** `services/message/internal/storage/postgres/feature.go:24`

```go
sqlQuery := "%" + req.Query + "%"
```

Символы `%` и `_` в пользовательском вводе не экранируются. Пользователь может маниулировать шаблоном LIKE.

### 12. Не проверяется `rows.Err()` после итерации
**Файлы:** `services/message/internal/storage/postgres/message.go:84`, `services/message/internal/storage/postgres/feature.go:50`

Если произошла ошибка сети во время итерации, она будет молча проглочена.

### 13. INSERT без ON CONFLICT для read receipts
**Файл:** `services/message/internal/storage/postgres/feature.go:53-69`

При повторном вызове `SetAsRead` будет ошибка уникального ограничения. Нужно использовать `INSERT ... ON CONFLICT ... DO UPDATE`.

### 14. Неправильная логика пагинации HasMore
**Файлы:** `services/message/internal/service/message.go:62-65`, `services/message/internal/service/feature.go:55-57`

```go
// НЕПРАВИЛЬНО: HasMore=true при любом количестве > 1
if len(messages) > 1 { isMore = true }

// ПРАВИЛЬНО: сравнивать с лимитом
isMore = len(messages) == int(req.Limit)
```

### 15. Параллельные goroutines для тривиальной конвертации
**Файл:** `services/message/pkg/utils/converter.go:42-59`

`ParallelConvert` использует goroutines для конвертации простых структур. Конвертация proto — тривиальная операция, оверхед от goroutines превышает пользу.

## Мелкие ошибки (P3)

### 16. `os.Kill` нельзя перехватить
**Файл:** `services/user/cmd/server/main.go:32`

```go
signal.Notify(sigChan, os.Interrupt, os.Kill) // os.Kill = SIGKILL, нельзя перехватить
```

Нужно использовать `syscall.SIGTERM`.

### 17. Signal handler недостижим
**Файл:** `services/user/cmd/server/main.go:29-45`

`server.GRPCSrv.MustRun()` блокируется вызовом `gRPCServer.Serve()`. Goroutine с signal handler на строке 34 никогда не выполнится до завершения `Serve`.

### 18. `print()` вместо `log` или `fmt.Println`
**Файл:** `server-gateway/cmd/app/main.go:4`

### 19. Непоследовательные имена конструкторов
- `NewMessageFuncService`
- `NewReactionService`
- `CreateFeatureService` — нарушает конвенцию `New*`

### 20. Дублирование кода между сервисами
- `InterceptorLogger` — идентичные функции в обоих сервисах
- Конфиги `PostgresCfg`, `GRPCCfg` — идентичные структуры
- `NewStorage` — одинаковая логика подключения к БД

## Архитектурные проблемы

### 21. Нет тестов
Во всём проекте нет ни одного `_test.go` файла. Нет unit-тестов, интеграционных тестов, тестов gRPC-обработчиков.

### 22. Дублирование protobuf timestamp
**Файл:** `pkg/protos/timestamp.proto`

Создана собственная копия `google.protobuf.Timestamp` вместо использования `google/protobuf/timestamp.proto`.

### 23. Server-gateway — мёртвый код
**Файлы:** `server-gateway/cmd/app/main.go`, `server-gateway/internal/app/restapi.go`

Содержит только `print("Hello, World!")` и пустой пакет.

### 24. Нет graceful shutdown для storage
**Файлы:** `services/user/internal/storage/postgres/storage.go:35-37`

Метод `Close()` существует, но никогда не вызывается при завершении работы.

### 25. Валидатор создаётся заново при каждом вызове
**Файл:** `services/user/internal/service/user.go:34`

`validator.New()` создаётся в каждом методе. Валидатор потокобезопасен и должен создаваться один раз.

## Сильные стороны проекта

1. **Правильная архитектура** — слоистая структура (gRPC → Service → Storage), использование интерфейсов
2. **Хорошие proto-определения** — комплексные и хорошо спроектированные
3. **Использование современных библиотек** — pgx, zap, validator, grpc-middleware
4. **Go Workspaces** — правильное использование для монорепозитория
5. **CI/CD** — GitHub Actions с linting и тестами (хотя тестов пока нет)
6. **Структура пакетов** — чёткое разделение по domain-driven design

## Заключение

Проект показывает понимание основ Go-архитектуры и микросервисов. Стажер выбрал правильные инструменты и паттерны, но допустил критические ошибки в реализации: data races, неправильную обработку ошибок, проблемы безопасности и отсутствие тестов. Основные усилия должны быть направлены на исправление P0 ошибок и добавление тестов.
